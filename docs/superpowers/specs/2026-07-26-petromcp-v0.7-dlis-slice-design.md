# petromcp v0.7 — DLIS slice design

Status: drafted 2026-07-26 from a feasibility spike. Not yet approved.
Predecessor: `2026-07-26-petromcp-v0.5-synthetic-facies-design.md`.

## Why this slice

DLIS is the format the neighbouring project does not touch, and the one that
is genuinely hard: binary, RP66 v1, and structurally richer than LAS. Owning it
is a stronger position than matching anyone on breadth of calculations.

It is also the first format where petromcp's structure is tested. LAS is one
flat curve set per file. DLIS is *N logical files, each with M frames, each
with K channels* — so the tools need an addressing scheme, which LAS never
forced us to design.

## What the spike established

Everything below was verified by running it, not read from documentation.

| Question | Answer |
|---|---|
| Can we generate synthetic DLIS? | **Yes.** `dliswriter` 1.2.0 writes files `dlisio` 1.0.4 reads back with well name, company, frame, index type, channel names, units, and values intact. |
| Can a channel be shared between frames? | **No.** RP66 v1 allows a channel in exactly one frame; `dliswriter` warns. Each frame needs its own index channel. |
| Can we generate multiple logical files? | **No.** `dliswriter` 1.2.0 fails with `ValueError: No dataset '<name>' found in the source data`. Its data resolution is not scoped per logical file. |
| How does `dlisio` fail on bad input? | **Loudly, always.** Truncated → `RuntimeError`; empty → `EOFError`; non-DLIS → `RuntimeError`; valid header with junk body → `RuntimeError`. Nothing degrades silently. |
| Are units constrained? | **Yes.** RP66 defines a controlled vocabulary (`gAPI`, `ft`, `ohm`, `mD`, `psi`, `us`, …). It contains no compound density unit, so `g/cm3` warns but round-trips. |

Two consequences worth stating plainly:

- **The ground-truth-manifest pattern transfers.** `dliswriter` becomes a
  dev-only dependency. petromcp itself never writes DLIS.
- **Multi-logical-file reading cannot be covered by generated data.** The tools
  must handle N logical files, but our generator can only produce one. That
  path needs a committed binary fixture, and we cannot author one with
  `dliswriter` either. See Open questions.

## Scope

In:

1. `read_dlis_file` — structure and metadata. No channel data.
2. `list_dlis_channels` — every channel with its frame, units, and length.
3. `read_dlis_channel` — one channel's values, token-budgeted like the LAS
   equivalent.
4. Synthetic DLIS generation reusing the existing facies model and defect
   catalogue.
5. A bad-DLIS fixture corpus, and tests that every tool survives every fixture.
6. Eval scenario 03 asserting against the emitted manifest.

Out:

- Writing DLIS. petromcp reads.
- LIS79, which `dlisio` also supports. Different format, different slice.
- Frame-to-frame merging or resampling. That is interpretation, not I/O.
- Anything that computes a petrophysical answer.

## Architecture

### Reuse, deliberately

`examples/sample_data/facies.py` and `defects.py` are pure array producers with
no LAS knowledge. The DLIS generator reuses both unchanged: same four facies,
same six defect kinds, same `WellTruth` manifest. Only the writer differs.

That was the point of separating them, and it is worth checking the claim holds
before writing new code — if either module turns out to have LAS assumptions
baked in, fix that rather than duplicating.

```
examples/sample_data/
  facies.py      unchanged, reused
  defects.py     unchanged, reused
  truth.py       EXTEND: frames alongside curves
  dlis_wells.py  NEW  DLIS well definitions (frames, channels per frame)
  dlis_generate.py NEW  the writer; dliswriter, dev-only
src/petromcp/
  models/dlis.py NEW  DLISSummary, LogicalFileInfo, FrameInfo, ChannelInfo, ChannelData
  tools/dlis.py  NEW  the three tools
  utils/dlis_open.py NEW  load + error translation, mirroring lasio_open
```

### Addressing

The design decision LAS never forced. A DLIS channel is identified by
`(logical file index, frame name, channel name)`, and channel names are not
unique across frames.

**Chosen:** explicit arguments with sensible defaults.

```python
read_dlis_channel(
    path: str,
    channel: str,
    frame: str | None = None,          # required only if ambiguous
    logical_file: int = 0,
    depth_start: float | None = None,
    depth_stop: float | None = None,
) -> DLISChannelData
```

If `channel` appears in exactly one frame of the named logical file, `frame`
may be omitted. If it appears in several, the tool raises and **names the
frames it appears in**, so the model's next call is correct rather than a
guess. Silently picking the first would produce a plausible wrong answer, which
is the worst outcome for a tool an LLM drives.

Rejected: a path string like `0/TRIPLE_COMBO/GR`. Compact, but it invents a
syntax the model has to learn and get exactly right, and errors become string
parsing failures rather than "that channel is in two frames, which did you
mean".

### Error translation

`dlisio` raises `RuntimeError` and `EOFError` with messages that name RP66
internals. Those are accurate and useless to an LLM. `utils/dlis_open.py`
translates them into one exception type carrying the path and a short
statement of what is wrong, mirroring how `path_validator` phrases its
refusals.

Note this is the opposite posture from LAS. There, `safe_index` degrades a
truncated file into a partial summary because `lasio` partially parses it and a partial
answer is genuinely useful. A DLIS that fails to load yields nothing at all, so
there is nothing to degrade to — the honest response is a clear error.

### Token budget

DLIS files carry far more channels than a LAS file carries curves; a real one
can hold hundreds across several frames. So:

- `read_dlis_file` returns structure only: logical files, frames, index types,
  channel counts. Never values.
- `list_dlis_channels` returns one row per channel and takes an optional
  `frame` filter. It reports channel *length* but no statistics, because
  computing statistics means reading every curve.
- `read_dlis_channel` keeps the 500-sample cap and the `downsampled` /
  `original_count` flags.

`summarize_dlis_curves` is deliberately **not** in this slice. The LAS
equivalent reads every curve to compute statistics, which is affordable for
five curves and not for two hundred. Doing it properly needs a channel filter
and a documented cost, and that is its own decision.

## Testing

Same order of priority as v0.5, for the same reasons.

1. **The manifest must not lie.** Generate, read back with `dlisio`, assert
   every recorded defect is present. Reuses the v0.5 test shape.
2. **Every tool survives every bad fixture.** The rule from CLAUDE.md: a fix at
   one call site is not a fix. All three tools run against all fixtures.
3. Facies and defect reuse: assert the generated DLIS carries the same curve
   relationships the LAS generator produces from the same seed. If they
   diverge, one of the writers is wrong.
4. Ambiguous-channel handling: a channel in two frames must raise and name
   both. This is the failure mode most likely to produce a confidently wrong
   answer.
5. Round-trip units: RP66's vocabulary must not silently change a unit.
6. Eval scenario 03 green.

Bad-DLIS corpus, from the spike's verified behaviours: `truncated.dlis`,
`empty.dlis`, `not_dlis.dlis`, `junk_body.dlis`.

## Build order

1. Confirm `facies.py` and `defects.py` really are format-agnostic.
2. `utils/dlis_open.py` + error-translation tests.
3. `models/dlis.py`.
4. `dlis_wells.py` + `dlis_generate.py` + the manifest-does-not-lie test.
5. Bad-DLIS corpus + the every-tool-every-fixture test.
6. `tools/dlis.py`, one tool at a time, TDD.
7. Server registration with read-only annotations.
8. Eval scenario 03.
9. Docs: tool reference, README table, a fourth walkthrough, changelog.

Commit on every green step.

## Open questions

These need answers before step 4, and two of them are judgement calls rather
than research:

1. **Multi-logical-file coverage.** `dliswriter` cannot produce one. Options:
   hand-author a binary fixture (slow, brittle, but real); find a
   public-domain sample DLIS with several logical files and commit it (licence
   must be checked); or declare N>1 out of scope for v0.7 and have
   `read_dlis_file` report only the first logical file with an explicit note.
   The last is honest but weak, since real service-company DLIS files routinely
   carry several.
2. **Density units.** RP66 has no `g/cm3`. Write it anyway and accept the
   warning (matches what real files do), or use an RP66-legal unit and diverge
   from the LAS generator. Affects test 3 above.
3. **`defects.NULL_VALUE` is LAS-specific and must be generalised.** Verified
   during step 1: `facies.py` and `defects.py` import nothing LAS-specific, so
   the reuse claim holds structurally — but `defects.py` hardcodes
   `NULL_VALUE = -999.25`, the LAS `~Well` NULL convention. Writing that into a
   DLIS channel would store a *real value of minus nine hundred*, not an absent
   marker, and every statistic computed over it would be wrong.

   Fix: `null_gap` should write `np.nan`, the format-neutral in-memory
   representation, and each writer encodes absence in its own convention
   (`lasio` already maps NULL to NaN on read, so the LAS path is unaffected).
   This is a small change to `defects.py` plus its tests, and it must land
   before the DLIS generator, not after.

4. **Whether `dliswriter` belongs in the dev group at all.** It pulls its own
   dependency tree into the dev environment for the sole purpose of generating
   test data. The alternative is committing a handful of small generated
   `.dlis` files as fixtures and dropping the dependency — losing
   parameterisation and the manifest pattern. I lean toward the dependency; the
   manifest pattern has already caught real bugs twice.

## Risks

- **`dliswriter` is the newer, less-proven library.** The multi-logical-file
  failure is evidence. If more limitations appear mid-build, fall back to
  committed fixtures rather than fighting it — the fixtures path is strictly
  simpler and only costs parameterisation.
- **DLIS structure invites scope creep.** Frames tempt merging, resampling, and
  index alignment. All of that is interpretation. If a tool starts needing to
  decide which frame is authoritative, stop.
- **`dlisio` pins matter.** It is a C++ extension; a version bump can change
  parse behaviour. Pin it, and let the weekly float job catch upstream drift.
